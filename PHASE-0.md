# Phase 0 — closing the security gaps (Oct 2026)

What changed in the code, and the steps only someone with the Firebase, Google Apps Script and GitHub
accounts can do. **Do them in this order.** Each step can be undone on its own.

## What is in this change

| | |
|---|---|
| `database.rules.json` | Real database rules. Who may read and write what now follows Settings → Users — the same ticks the pages already check — instead of "any signed-in account". Generated by `rules/build-rules.cjs`; tested by `rules/test/` (17 tests against the Firebase emulator). |
| `js/app.js`, `orders-page.html` | `escJs()` for text inside buttons' `onclick`. A quote in a plate, client or file name could run code, and a name like *O'Brien* broke the button. Three client names on the Orders page were not escaped at all. |
| both pages | Drive uploads carry the sign-in token. |
| `apps-script/upload-auth.gs` | The check the upload script runs on that token. |

What the rules do, in short:

- **No access until the admin ticks a page.** A new or unknown account can only create its own "no access yet" record — it can no longer read trucks, drivers, passports, orders or PIN hashes, and can never give itself a role or a page.
- **FleetGuard accounts** read everything under `fleetguard` and save what FleetGuard saves; they cannot write orders (the Orders page owns them).
- **Orders accounts** read only what the Orders page uses (trucks, drivers, trailers, orders, offload reports, attention requests, Finance PIN, date format) — not job cards, the audit trail or the admin PIN.
- **Only an active `Admin`** reads Settings → Users, changes anyone's access, sets the admin PIN or sets the Finance PIN.
- **Turned-off accounts** get nothing, whatever their role.

## Steps, in order

### 1. Before anything: make sure there is an Admin
Firebase console → **Realtime Database → Data → users**. At least one person who manages users must have
`role: "Admin"` and not `active: false`. After step 3 **only** Admin accounts can open Settings → Users or change
the admin or Finance PIN. (Settings → Users → Job-card role → Admin, while the old rules are still on.)

Also: **does anything other than FleetGuard and the Orders page use the `rag-os-e9382` database?** The new
rules allow only `users/` and `fleetguard/`. If something else reads or writes there, say so first.

### 2. Put this branch live (GitHub)
Merge `phase0-security` into `main` (GitHub Pages publishes `main`). The pages work the same under the old and the
new rules, so this can go first.

### 3. Publish the rules (Firebase console)
1. **Realtime Database → Rules.** Copy what is there now and keep it — that is the way back.
2. Replace it with the contents of `database.rules.json` → **Publish**.
3. Straight away, sign in with an **Admin**, a **FleetGuard-only** and an **Orders-only** account and open each
   page. If anything says "permission denied", paste the old rules back and send the message.

### 4. Turn on the upload check (Google Apps Script)
Follow the steps at the top of `apps-script/upload-auth.gs`. Edit the **existing** deployment so the URL stays the
same. Then upload a photo from FleetGuard and from the Orders page.

### 5. Look at the accounts (Firebase console → Authentication → Users)
Disable any account nobody recognises. **Leave "Enable create (sign-up)" on for now:** Settings → Users → *Add user*
creates accounts through it, and with the new rules a self-made account sees nothing. Phase 2 (one login through
3 RAG Pay) removes this.

### 6. Change both PINs to 6 digits (FleetGuard → Settings → Admin Security)
Any account with page access can still read the PIN hashes, and a 4–6 digit PIN can be guessed from its hash.
That is fixed for good in Phase 2, when Finance and Admin become roles the database checks. Until then, change
the PINs now that strangers can no longer read them, and use 6 digits.

### 7. Stop changing `main` directly (GitHub, repo owner)
- Create a `develop` branch and make it the default; work lands there, `main` only through a pull request.
- Settings → Branches → protect `main`: require a pull request. (Free for public repositories.)

## Changing the rules later
Edit `rules/build-rules.cjs`, never `database.rules.json`, then:

```bash
cd rules && npm install && npm test
```

`npm test` rebuilds the JSON and runs the tests (needs Java for the emulator). Commit both files.
